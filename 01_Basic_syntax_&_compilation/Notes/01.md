## 1) The source schema

Open users.proto. It is the source of truth:

```proto
syntax = "proto3";
package users;

message User {
  int64 id = 1;
  string name = 2;
  repeated RoleType roles = 3;
}

enum RoleType {
  ROLE_UNSPECIFIED = 0;
  ROLE_ADMIN = 1;
  ROLE_USER = 2;
}
```

Important ideas:

- `proto3` means modern protobuf syntax.
- `field = number` is the wire tag. This matters for binary encoding.
  - `id` is field 1
  - `name` is field 2
  - `roles` is field 3
- `repeated` means a slice in Go.
- `enum` values get numeric codes on the wire.

So the concept is: the proto defines a binary data format, and the generated Go code gives you a convenient type to work with.

## 2) The generated enum

In the Go file, this appears:

```go
type RoleType int32

const (
    RoleType_ROLE_UNSPECIFIED RoleType = 0
    RoleType_ROLE_ADMIN       RoleType = 1
    RoleType_ROLE_USER        RoleType = 2
)
```

This is basically:

- a Go integer type
- with named constants for each enum value

So instead of writing magic numbers like `1`, you can write:

```go
user.Roles = []users.RoleType{
    users.RoleType_ROLE_ADMIN,
    users.RoleType_ROLE_USER,
}
```

The generated map below:

```go
var (
    RoleType_name = map[int32]string{
        0: "ROLE_UNSPECIFIED",
        1: "ROLE_ADMIN",
        2: "ROLE_USER",
    }
)
```

is used to convert:

- number -> name (`1 -> "ROLE_ADMIN"`)
- name -> number (`"ROLE_ADMIN" -> 1`)

That’s why protobuf enums are safe and self-describing.

This is the heart of the file:

```go
type User struct {

    sizeCache     protoimpl.SizeCache
```

This maps directly to the proto:

| Proto field                    | Go field           |
| ------------------------------ | ------------------ |
| `int64 id = 1;`                | `Id int64`         |
| `string name = 2;`             | `Name string`      |
| `repeated RoleType roles = 3;` | `Roles []RoleType` |

The `state`, `unknownFields`, and `sizeCache` fields are not for your app logic. They are internal protobuf runtime state used to:

- track message metadata
- store unknown fields
- optimize serialization size
- support reflection and encoding

You generally ignore them.

## 4) Why there are methods like `Reset`, `String`, `ProtoReflect`

These are boilerplate generated methods.

### `Reset()`

```go
func (x *User) Reset() {
    *x = User{}
    ...
}
```

This clears the message, like setting it back to zero value.

### `String()`

```go
func (x *User) String() string {
    return protoimpl.X.MessageStringOf(x)
}
```

This gives a printable representation, useful for debugging.

### `ProtoReflect()`

```go
func (x *User) ProtoReflect() protoreflect.Message
```

This is the big one. It gives the message a protobuf reflection interface so the runtime can:

- serialize the message
- deserialize it
- inspect fields
- support dynamic encoding/decoding

This is why the generated code depends on `google.golang.org/protobuf/...` packages.

## 5) `GetId`, `GetName`, `GetRoles`

These are simple nil-safe getters:

```go
func (x *User) GetId() int64 {
    if x != nil {
        return x.Id
    }
    return 0
}
```

They exist because protobuf style often wants getters like `GetName()` instead of direct field access, especially in generated code for interop and nil-safety.

In normal Go code, you can usually just do:

```go
u := &users.User{Id: 42, Name: "Alice"}
fmt.Println(u.Id)
```

But `GetId()` is the generated “official” accessor pattern.

## 6) The raw descriptor

This part is important:

```go
const file_users_proto_rawDesc = "" +
    "\n" +
    "\vusers.proto..."
```

This is the encoded schema as a byte string. It is the serialized version of the `.proto` definition.

Then the runtime builds descriptors from it:

```go
out := protoimpl.TypeBuilder{
    File: protoimpl.DescBuilder{
        GoPackagePath: reflect.TypeOf(x{}).PkgPath(),
        RawDescriptor: ...,
        NumEnums: 1,
        NumMessages: 1,
    },
    ...
}.Build()
```

This is how the library knows:

- there is an enum `RoleType`
- there is a message `User`
- which fields exist
- their tags and types
- their package name

So the generated file is not just data classes — it also includes the schema metadata needed by the protobuf runtime.

## 7) Why this file is “generated” and not hand-written

Because the compiler produces it from the proto definition. If you change the `.proto` file later, you regenerate the Go file, and it will update all the struct fields and methods.

That’s why these files usually say:

```go
// Code generated by protoc-gen-go. DO NOT EDIT.
```

The generated code is mechanical and exact. You are meant to edit the `.proto`, not the generated Go file.
